# Бачення, бізнес-цілі та позиціонування для enterprise

## Короткий виклад для керівництва

- **Керований контур:** трекер фіксує намір і обмеження; автоматизація виконує **розкладені, ідемпотентні** ролі з **детермінованим** вибором тикетів.
- **Потік без штампеду:** одна автоматична роль на слот; черги видно в Linear (і через snapshot-утиліти).
- **Аудитованість:** автоматичні дотики прив’язані до тикетів, запусків workflow і позначених коментарів.
- **Переносимість:** оркестрація — **GitHub Actions + Node**; інтеграції трекера й агента задумані як **адаптери** (див. розділи розширення нижче).

Цей стек автоматизації спроєктований як **скінченний, аудитований контур керування** навколо постачання продукту: люди задають намір і обмеження у трекері; машини виконують повторювані ролі за розкладом з **ідемпотентними** промптами та **детермінованим** вибором тикетів.

**Коротко для стейкхолдерів:** [Executive brief](executive-brief.md).

## Бізнес-цілі

| Ціль | Як цьому сприяє дизайн |
|------|------------------------|
| **Передбачуваний потік** | Одна роль на слот cron уникає «штампеду» агентів; черги видно в Linear і через `agent-queue-snapshot.mjs`. |
| **Аудит** | Кожен автоматичний дотик прив’язаний до тикету, запуску workflow і позначених коментарів (`[GitHub SDLC:…]` / `[GitHub SDLC daily-audit:…]`). |
| **Якісні ворота** | Промпт розробника вимагає lint, typecheck, тести, збірку, smoke E2E перед PR; роль безпеки споживає JSON Snyk. |
| **Операційна ясність** | Backlog залишається за людьми; **Todo** + фільтри проєкту визначають, що може торкнутися автоматизація — без «сюрпризних» виборів. |
| **Гнучкість щодо постачальників** | Оркестрація — звичайні GitHub Actions + Node-скрипти; постачальник агента (сьогодні Cursor) **замінний** за тим самим контрактом запуску. |

## Керована станова машина (чому це масштабується)

Смуга SDLC поводиться як **керована станова машина** (явні стани, переходи та охорони):

- **Стани** — колонки Linear (`Backlog`, `Todo`, `In Progress`, …).
- **Події** — дії людей (наприклад «перенести в Todo») або ребра автоматизації (`pick-*` → Cloud Agent → мітки / PR).
- **Охоронні умови** — мітки та членство в проєкті (`ready:developer`, `stage:intake`, pre-release проєкт тощо).

Ця модель важлива для розмов про відповідність: можна посилатися на **явні правила переходів** у pick-скриптах і промптах замість ad-hoc поведінки ботів.

## Розширення: замінити Linear на Jira (або інший трекер)

Поверхня зв’язку навмисно мала:

1. **Pick-скрипти** (`scripts/pick-*.mjs`) — зараз викликають Linear GraphQL з `IssueFilter`. Реалізація на Jira запитувала б JQL і повертала той самий **рядок ключа** issue для оркестратора.
2. **`cloud-agent-launch.mjs`** — резолвить метадані через `dist/cli.js get`; замінити на `jira get ISSUE-123` або тонкий адаптер.
3. **Промпти** — згадують «Linear» у тексті; замінити на «Jira» та семантику полів (пріоритет, компоненти), зберігаючи **семантику ролей** (intake, BA, dev).
4. **Секрети** — `LINEAR_API_KEY` → `JIRA_API_TOKEN` + base URL; змінні GitHub для ID проєкту/борду замість `LINEAR_SDLC_PROJECT_ID`.

GitHub Actions **залишаються** планувальником; змінюються лише **провайдер issue** та **CLI**. Під час міграції можна навіть запускати **обидва** трекери, дублюючи workflow з різними префіксами env.

## Розширення: інші постачальники агентів або self-hosted runner’и

`cloud-agent-launch.mjs` — HTTP-клієнт до **Agents API Cursor**. Той самий патерн оркестрації підходить для:

- Іншого керованого API агентів (якщо приймає репо + промпт + іменування гілок).
- **Self-hosted** job runner’ів з Codex / локальним LLM — за умови дотримання контракту: checkout, іменування гілок (`fix/ELM-XX-auto`), тіло PR з `Closes ELM-XX` та оновлення Linear/Jira.

**Пакет промптів** (`cloud-prompts/*.md` + `.cursor/skills`) лишається переносним активом.

---

## Розширення: оркестрація поза GitHub Actions

Тригери — «запустити Node, потім за потреби запустити агент». Ті самі скрипти працюють локально або в:

- **GitLab CI / CircleCI / Buildkite** — розклад + секрети + checkout.
- **Argo / Airflow** — якщо потрібен fan-out між репо (наприклад нічні аудити багатьох продуктів).

Тримай pick/launch як **звичайний Node** для мінімальної вартості інтеграції.

---

## Щоденні аудити як другий, не-SDLC контур

Ролі tech architect, QA architect і security officer **не споживають** чергу pre-release SDLC. Вони пишуть у **окремі проєкти Linear** з жорсткими правилами «без вигадування» — підходить для **реєстрів ризиків** і **архітектурних рад** без засмічення дошки спринту.

## Підсумок

- **Модель керування рівня enterprise** = явні стани, охорони, маркери аудиту та замінні адаптери — не «магічна» інтеграція одного вендора.
- **Поточний стек** = Linear + GitHub Actions + Cursor Cloud Agent + Snyk — задокументований як **одна реалізація** цього патерну.
