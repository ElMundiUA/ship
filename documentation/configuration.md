# Configuration

This is the technical reference for repo-level Ship wiring. Product owners usually do not need this page. Use it when you are implementing local setup, debugging `shipctl`, reviewing generated files, or keeping agent instructions versioned.

For the product setup path, start with [Getting started](/getting-started). For day-to-day review, use [Operating](./operating.md).

## What configuration is for

Ship keeps product language simple, but the repo still needs precise files:

- `.ship/config.yml` records the stack and local Ship settings.
- `.ship/cache/` stores fetched artifacts for local/offline use.
- `.ship/shipctl.lock.json` records artifact versions and hashes when lock output is enabled.
- Agent rule files such as `AGENTS.md`, `CLAUDE.md`, or `.cursor/rules/*.mdc` carry versioned instructions.
- Generated workflow files connect host events or schedules to Ship-owned routines.

Do not put secrets in any of these files. Use GitHub/CI secrets, Ship repo secrets, or the platform secret manager.

## On-disk layout

| Path | Tracked? | Purpose |
| --- | --- | --- |
| `.ship/config.yml` | committed | Repo-level Ship configuration. |
| `.ship/shipctl.lock.json` | committed when generated | Resolved artifact versions and hashes. |
| `.ship/cache/` | usually ignored | Local artifact body cache. |
| `.ship/state.json` | ignored | Mutable local state for sync and CLI operations. |
| `.ship/knowledge/*.md` | committed when used | Repo knowledge mirrored into the workspace. |
| `.ship/feedback-drafts/*.md` | ignored | Local drafts before feedback submission. |
| Agent rule targets | committed | Versioned instructions installed for Cursor, Claude, Codex, Copilot, and other agents. |

The CLI should own marker-delimited blocks inside agent rule targets. Put custom notes outside the markers.

## Minimal config shape

```yaml
version: 2
shipctl_min: "0.12.0"

stack:
  tracker: "github-issues"
  ci: "gh-actions"
  agents: ["cursor", "codex"]
  language: "ts"
  preset: "web-app"

api:
  base_url: "https://ship.elmundi.com"
  channel: "stable"
  offline_ok: true

artifacts:
  auto_update: true
  pins: {}

telemetry:
  share: false
```

The exact schema is enforced by the CLI. When this page and `cli/lib/config/schema.mjs` disagree, the code wins.

## Important fields

### `stack`

Describes the repo so Ship can install the right rules and checks.

| Field | Meaning |
| --- | --- |
| `tracker` | Issue tracker shape, for example `linear`, `github-issues`, `jira`, or `none`. |
| `ci` | CI provider, for example `gh-actions` or `manual`. |
| `agents` | Agent ids whose rule files should be installed or verified. |
| `language` | Primary language hint. |
| `preset` | Starter bundle such as `web-app`, `api-backend`, `mobile-app`, `cli`, `monorepo`, or `adoption-minimum`. |

### `api`

Controls where the CLI fetches catalog data and whether cached artifacts can be used while offline.

### `artifacts`

Pins keep specific artifact versions stable. Use pins when a prompt, rule, or adapter must not drift during a rollout.

```yaml
artifacts:
  pins:
    pattern/role-developer: "1.4.2"
    collection/agent-rules-cursor: "^3.0.0"
```

### `telemetry`

Telemetry is opt-in. Keep it off unless the workspace owner has decided to share usage events.

## Automations and routines

Repo-level automation wiring is implementation detail. Product docs call it **automation**; CLI and config may call it a **routine** or legacy **lane**. New public prose should not lead with those words.

When you do need the technical layer, keep these rules:

- Use the current schema generated by `shipctl`.
- Keep trigger, scope, and pattern references in one reviewable change.
- Commit generated workflow changes with the config change they depend on.
- Prefer `shipctl verify` over manual inspection after edits.

## Local commands

Use [/cli](/cli) for full syntax. The most common configuration commands are:

```bash
shipctl doctor
shipctl verify
shipctl sync
shipctl config show
shipctl config validate
shipctl init --copy-rules
```

Run these from the repo root unless you pass an explicit `--cwd`.

## Review checklist

Before merging a configuration change, confirm:

- No secret values are committed.
- Agent rule marker blocks are intact.
- The changed artifact versions are intentional.
- The tracker, CI, and agents match what the repo actually uses.
- `shipctl verify` passes, or every warning has a recorded reason.
- Any workflow generated from Ship config is included in the same PR.
