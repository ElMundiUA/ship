# Lanes

A *lane* is a triggered execution unit declared in your repo's
`.ship/config.yml` under the `lanes:` block. One lane ↔ one call to
`shipctl run`. Lanes are how Ship replaces the old "workflow = GitHub
Actions file" model: your `.ship/config.yml` is the spec, Ship
generates the thin wrappers, and the Console surfaces what's actually
running where.

This page is the operator reference: what you put in the YAML, what
`shipctl` does with it, and how the Console and webhooks keep the
picture fresh. For the raw schema — field-by-field, with defaults and
validation exit codes — see [Configuration → `lanes`](/docs/configuration#lanes).

The normative spec is
[RFC-0007](/docs/protocol/rfc-0007-lanes-and-run-agent) (and the
catalog-side rename in [RFC-0008](/docs/protocol/rfc-0008-catalog-reform)).
When this page and `cli/lib/config/schema.mjs` disagree, the CLI wins.

## Anatomy of a lane

```yaml
version: 2
shipctl_min: "0.12.0"

lanes:
  pr_review:
    kind: event
    on: pull_request
    pattern: flow-pr-self-review

  daily_retro:
    kind: schedule
    cron: "0 9 * * 1-5"
    patterns:
      - flow-daily-retro

  seed_knowledge:
    kind: once
    pattern: onboard-seed-knowledge
    idempotency:
      key: seed-knowledge-v1
      store: file
      reset_on: version-change
```

Keys under `lanes:` are lane ids matching `/^[a-z0-9][a-z0-9_-]{0,63}$/`
(ids starting with `ship_` are reserved). Each lane declares exactly one
*trigger* (`kind`) and exactly one of `pattern:` / `patterns:`.

### Multiple patterns per lane (RFC-0008 C3)

A lane can fan out across several patterns that share a trigger — the
`tech_debt` audit, for example, runs a technical-architect review, a
QA review and a security review on the same schedule:

```yaml
lanes:
  tech_debt_audit:
    kind: schedule
    cron: "0 6 * * 1"
    patterns:
      - role-tech-architect
      - role-qa-architect
      - role-security-officer
```

Rules:

- `pattern: <id>` (scalar) and `patterns: [<id>, …]` (list) are
  mutually exclusive — declare exactly one.
- `patterns` must be a non-empty list of existing pattern ids.
- `shipctl run --lane <id>` currently requires a single-pattern lane;
  multi-pattern execution (parallel agent fan-out) lands in
  RFC-0008 C3.2. Until then a lane with `patterns.length > 1` is
  rejected by `shipctl run` with a clear error and dispatched by the
  dashboard through a parametric workflow instead.

## Triggers

| `kind`     | Extra field | Fires when                                                                 | Typical use                                |
|------------|-------------|----------------------------------------------------------------------------|--------------------------------------------|
| `once`     | `idempotency: { key, store?, reset_on? }` | A bootstrap moment, dispatched manually or by the dashboard; guarded by a ledger key so duplicate runs no-op. | Seeding, one-off backfills, first-time installs |
| `event`    | `on: pull_request \| push \| workflow_run \| deployment_status` (+ optional `when: {…}`) | A matching webhook from the code host. | PR gates, code-review lanes, CI follow-ups |
| `schedule` | `cron: "<5-field>"` (+ optional `cron_tz`) | UTC cron, 5 fields, GitHub Actions syntax. | Daily/weekly ceremonies, drift checks |

Lanes are the *only* place triggers live. `shipctl` does not accept
ad-hoc workflow YAMLs any more; the files under `.github/workflows/`
named `ship-<lane_id>.yml` are generated by
[`shipctl lanes install`](/cli#shipctl-lanes-install) and carry a
`# ship-cli: lanes v1` banner. Hand-edits outside the banner survive
re-runs; edits inside the banner will be overwritten.

## Required fields (by `kind`)

| `kind` | Required extra keys | Validator message when missing |
|--------|--------------------|--------------------------------|
| `once`     | `idempotency.key` (matches `/^[a-z0-9][a-z0-9_.-]{0,127}$/`). `store` and `reset_on` are optional (default: `file`, `version-change`). | `lanes.<id>.idempotency: must be an object (kind=once requires it)` |
| `event`    | `on: …` (one of the four event types). `when:` is optional and forwarded to the reusable workflow. | `lanes.<id>.on: must be one of pull_request|push|workflow_run|deployment_status` |
| `schedule` | `cron: "<5-field cron>"`. `cron_tz` is optional (default UTC). | `lanes.<id>.cron: must be a 5-field cron expression` |

All lanes additionally need `kind:` and one of `pattern:` / `patterns:`.
Anything else you add to a lane block is carried through to the backend
as opaque forward-compat payload; schema v2.x may grow more official
fields (`inputs:`, explicit `timeout:`, …) but your extra keys will
not cause a hard error today — they surface as `unknown key (ignored,
preserved on write)` warnings.

## What `shipctl` does with a lane

Four commands deal with lanes directly:

- **`shipctl migrate`** — one-shot upgrade from v1 → v2. Backs up the
  current file to `.ship/config.yml.bak`, moves
  `stack.agent.provider` → `agent.default.provider`, and translates a
  legacy `lanes: [id, id, …]` list into the v2 lanes map using preset
  defaults. Safe to re-run: already-v2 configs exit `0` with
  `no changes`.
- **`shipctl lanes install`** — reads `.ship/config.yml`, renders
  one `.github/workflows/ship-<lane>.yml` wrapper per declared lane
  that calls `ElMundiUA/ship/.github/workflows/run-agent.yml@vN`
  (the `ref` defaults to `v<shipctl_min>`). Banner-guarded with
  `# ship-cli: lanes v1`. Refuses to overwrite a non-Ship file
  without `--force`. Idempotent — running it twice is a no-op.
  `shipctl lanes remove` only deletes files it owns.
- **`shipctl run --lane <id>`** — the single execution entry point.
  Today's scope: `kind: once` runs end-to-end (resolve the pattern,
  check the idempotency marker, emit the prompt on stdout, write the
  marker, POST the callback). `kind: event` and `kind: schedule` are
  parsed, validated, and reported as a `status: noop` — they rely on
  `shipctl lanes install`-generated wrappers that GitHub triggers
  and Phase 3 of RFC-0007 wires the reusable workflow.
  `--offline` resolves patterns exclusively through
  `.ship/shipctl.lock.json`.
- **`shipctl sync --lock`** — materialises every lane's pattern into
  `.ship/cache/` and writes `.ship/shipctl.lock.json`. The lockfile is
  safe to commit and is the reproducibility anchor for `run --offline`.

If you're installing Ship for the first time, `shipctl init` drops a
starter `lanes:` block for you and runs `shipctl lanes install` to
generate the matching wrappers.

## What the backend does with a lane

Two things:

1. **Projects it into a `lanes` table** that the Console reads. The
   table is a cache — the YAML file is the source of truth — so
   toggling a lane on/off through the API is *not* supported. You
   edit the YAML and push. The cache refreshes automatically when a
   push to the default branch touches `.ship/config.yml`, and you can
   force a re-pull with the "Sync now" button on `/lanes`.
2. **Reconciles runs.** When GitHub sends a `workflow_run.completed`
   event for `ship-<lane_id>.yml`, the backend pins
   `last_run_at` / `last_run_status` on the matching lane row. That's
   what powers the freshness badge in the Console without polling
   GitHub per page load.

## The Console `/lanes` page

`/lanes` is the Lanes hub. It's a tabbed surface (since the 2026-04-22
"Lanes hub + Requests — 3-phase overhaul" and the same-day "Lanes UI
redesign: weekly calendar + Outlook-style schedule wizard") with
three tabs:

- **Active** — a Mon–Sun × 24h UTC weekly calendar. `kind: schedule`
  lanes are plotted on the grid using the cron expression (weekly and
  daily presets render cleanly; arbitrary cron expressions fall back
  to their next occurrence). `kind: event` lanes appear in a strip
  below the calendar, grouped by event type. Clicking any block opens
  a detail drawer with the lane's YAML, recent runs, and an
  "Edit schedule" deep-link into the Library tab pre-seeded with the
  current cron.
- **Library** — a card grid of lane recipes keyed on `kind`. Each
  card shows a **kind badge** (`once` / `event` / `schedule`), a
  one-line description from the pattern, and inline controls:
  *Add*, *Edit schedule* (launches the Outlook-style
  **Schedule Wizard** — Daily / Weekly / Monthly presets instead of
  raw cron), and *Remove*. A `+ Author custom` card hands off to the
  custom-lane editor; all saves flow through a PR proposal against
  the customer repo.
- **Requests** — ad-hoc one-shot dispatcher backed by the new
  `adhoc-agent-run.yml` workflow + `AgentRequest` model. It is
  actively under development (landed 2026-04-22); use it to kick off
  a pattern outside of any declared lane. Recent dispatches are
  listed with GH Actions deep-links.

Per-lane detail (`/lanes/<lane_row_id>`) shows the full raw config,
sync source (`<ref_sha>:.ship/config.yml`), and up to 20 recent runs
keyed to the lane.

See [RFC-0008](/docs/protocol/rfc-0008-catalog-reform) for the
catalog reform that underpins the Library tab's ids
(`role-*`, `flow-*`, `scan-*`, `op-*`, `onboard-*`, `common-*`).

## Migrating from the old "workflow artifact" world

RFC-0007 removed `artifact_kind=workflow` from the public surface.
What used to be a workflow artifact is now a lane declared in
`.ship/config.yml`:

| Before                                             | After                                                                                                |
|----------------------------------------------------|------------------------------------------------------------------------------------------------------|
| `.github/workflows/ship-pr-and-ci-gate.yml`        | `lanes.pr_review:` — `kind: event`, `on: pull_request`, `pattern: flow-pr-self-review`              |
| `.github/workflows/ship-scheduled-sdlc-lane.yml`   | `lanes.daily_retro:` — `kind: schedule`, `cron: "0 9 * * 1-5"`, `pattern: flow-daily-retro`          |
| `.github/workflows/ship-onboard-seed-knowledge.yml`| `lanes.seed_knowledge:` — `kind: once`, `idempotency: { key: seed-knowledge-v1 }`, `pattern: onboard-seed-knowledge` |

The wrapper filenames survive as starter scaffolding (e.g.
`scheduled-sdlc-lane.yml` is still the filename the starter renderer
emits, even though `scheduled-sdlc-lane` is no longer a pattern id).
`shipctl lanes install` regenerates them from the v2 lane block.

If your repo still ships a hand-written workflow that hasn't been
migrated, the generator will refuse to overwrite it (no
`ship-cli: lanes v1` banner); delete the file, pass `--force`, or
migrate your config through `shipctl migrate`.

## Cookbook

### Add a new lane

1. Edit `.ship/config.yml`:

    ```yaml
    lanes:
      friday_retro:
        kind: schedule
        cron: "0 15 * * FRI"
        pattern: flow-daily-retro
    ```

2. `shipctl lanes install` to write
   `.github/workflows/ship-friday_retro.yml`.
3. `shipctl sync --lock` to refresh `.ship/shipctl.lock.json` with
   the new pattern.
4. Commit `.ship/config.yml`, the generated wrapper, and the updated
   lockfile in the same PR. The Console picks it up on the next push
   to the default branch.

### Pause a lane temporarily

Comment out (or delete) the lane block and push. The backend cleans
up the `lanes` row on the next webhook tick; the generated wrapper
will stop being rendered by `shipctl lanes install` on the next run.
Use `shipctl lanes remove --only <id>` to drop the wrapper file (it
only deletes files carrying the Ship banner).

If you want a "pause" that keeps the wrapper file on disk, wrap the
wrapper's `on:` block with a GitHub Actions `if:` guard — but note
that most teams find "delete + re-add" simpler and more auditable.

### Trigger a lane manually from the UI

The intended path as of 2026-04-22 is the **Requests** tab on
`/lanes` — it dispatches a one-shot `adhoc-agent-run.yml` with the
pattern you select and streams the run back into the hub. That tab is
actively under development (landed in the "Lanes hub + Requests"
overhaul); don't build CI on top of it yet.

For a stable manual override today, use the native GitHub Actions
**Run workflow** menu on any `ship-<lane_id>.yml` wrapper. Wrappers
expose `ship_run_id` and `ship_callback_url` inputs so the run
reports back to the dashboard the same way a scheduled run would.

### Keep the `lanes` table in sync

In normal operation you don't have to do anything — push-to-default
keeps the cache fresh. Use "Sync now" on `/lanes` when:

- you rewrote history and the webhook didn't fire;
- you're debugging a parse error and need the backend's take on the
  current YAML;
- you just flipped a lane on/off and want the Console to reflect it
  without waiting for the next push.

## Troubleshooting

| Symptom                                                                | Cause                                                                                                    | Fix                                                                                    |
|------------------------------------------------------------------------|----------------------------------------------------------------------------------------------------------|----------------------------------------------------------------------------------------|
| `/lanes` shows no lanes despite a `lanes:` block in `.ship/config.yml` | Either (a) `.ship/config.yml` wasn't pushed to the default branch yet, or (b) webhook delivery hasn't landed. | Push the commit; if the webhook is lost, click **Sync now** on the repo card.          |
| "Missing `.ship/config.yml`" on sync                                   | Repo's default branch has no `.ship/config.yml`.                                                         | Run `shipctl init` or point the `default_branch` at the branch that has it.            |
| `shipctl run --lane X` exits 2                                         | `.ship/config.yml` is still v1.                                                                           | Run `shipctl migrate`, review `.ship/config.yml.bak`, commit the new v2 file.          |
| Lane row shows kind `event` but run never fires                        | The wrapper file wasn't regenerated after the YAML change.                                                | Re-run `shipctl lanes install`, commit the updated wrapper.                             |
| `shipctl lanes install` refuses to overwrite `.github/workflows/ship-<id>.yml` | The existing file lacks the `# ship-cli: lanes v1` banner; the generator assumes it's hand-authored and won't clobber it. | Delete the file or pass `--force` to replace it.                                        |
| Lane row stays `running` forever                                       | `workflow_run.completed` webhook delivery failed.                                                         | Re-send the delivery from the GitHub App settings → Advanced → Recent deliveries.       |
| `shipctl sync --lock` reports unresolved entries                       | A lane references a pattern id that isn't published on the configured channel.                           | Fix the pattern id (see RFC-0008 for the current naming), or switch to `channel: edge`. |
