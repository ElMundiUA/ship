# Lanes

A *lane* is a triggered execution unit declared in your repo's
`.ship/config.yml` under the `lanes:` block. One lane ↔ one call to
`shipctl run`. Lanes are how Ship replaces the old "workflow = GitHub
Actions file" model: your `.ship/config.yml` is the spec, Ship
generates the thin wrappers, and the Console surfaces what's actually
running where.

This page is the operator reference: what you put in the YAML, what
`shipctl` does with it, and how the Console and webhooks keep the
picture fresh.

The normative spec is
[RFC-0007](/docs/protocol/rfc-0007-lanes-and-run-agent). Where this
page and the RFC disagree, the RFC wins.

## Anatomy of a lane

```yaml
version: 2
lanes:
  pr_review:
    event: pull_request
    pattern: pr-and-ci-gate

  daily:
    schedule: "0 9 * * *"   # UTC
    pattern: scheduled-sdlc-lane

  seed:
    once: install
    pattern: onboard-seed-knowledge
    idempotency_key: seed-v1
```

Keys under `lanes:` are lane ids (`[a-z][a-z0-9_-]{0,62}`). Each lane
declares exactly one *trigger* and the *pattern* Ship should run when
the trigger fires.

### Triggers

| Trigger   | Fires on                                                                                 | Typical use                               |
|-----------|------------------------------------------------------------------------------------------|-------------------------------------------|
| `event`   | A matching webhook from the code host — `pull_request`, `push`, `workflow_dispatch`, …    | PR gates, code-review lanes, CI follow-ups |
| `schedule`| UTC cron (5 fields, standard GitHub Actions syntax)                                       | Daily/weekly ceremonies, drift checks      |
| `once`    | A bootstrap moment — `install` (first time the lane is installed)                         | Seeding, one-off backfills                 |

Lanes are the *only* place triggers live. `shipctl` does not accept
ad-hoc workflow YAMLs any more; the files under `.github/workflows/`
named `ship-<lane_id>.yml` are generated by
[`shipctl lanes install`](/cli#shipctl-lanes-install) and should not
be edited by hand.

### Required fields

| Field            | Required    | Purpose                                                                 |
|------------------|-------------|-------------------------------------------------------------------------|
| one of `event` / `schedule` / `once` | yes | Trigger discriminator.                                      |
| `pattern`        | recommended | Pattern id resolved through the catalog at run time.                   |
| `idempotency_key`| for `once`  | Ledger key; duplicate runs with the same key are no-ops.               |

Anything else you add to a lane block is carried through to the
backend as opaque forward-compat payload; schema v2.x may grow
official fields (`inputs:`, `timeout:`, …) but your extra keys will
not cause a hard error today.

## What `shipctl` does with a lane

Three commands deal with lanes directly:

- **`shipctl lanes install`** — reads `.ship/config.yml`, materialises
  the lockfile, and writes `.github/workflows/ship-<lane_id>.yml`
  wrappers that call the reusable `run-agent.yml` from this repo.
  Idempotent.
- **`shipctl run <lane_id>`** — the single execution entry point. Ship
  never runs anything else. `--offline` forces pattern resolution
  through the lockfile.
- **`shipctl sync --lock`** — pins patterns into `shipctl.lock.json`
  and pre-populates `.ship/cache/` so `--offline` runs have a
  reproducibility anchor.

If you're installing Ship for the first time, `shipctl init` drops a
starter `lanes:` block for you and runs `shipctl lanes install` to
generate the matching wrappers.

## What the backend does with a lane

Two things:

1. **Projects it into a `lanes` table** that the Console reads. The
   table is a cache — the YAML file is the source of truth — so
   toggling a lane on/off through the API is *not* supported. You
   edit the YAML and push. The cache refreshes automatically when a
   push to the default branch touches `.ship/config.yml`, and you can
   force a re-pull with the "Sync now" button on `/lanes`.
2. **Reconciles runs.** When GitHub sends a `workflow_run.completed`
   event for `ship-<lane_id>.yml`, the backend pins
   `last_run_at` / `last_run_status` on the matching lane row. That's
   what powers the freshness badge in the Console without polling
   GitHub per page load.

## The Console `/lanes` page

`/lanes` renders every lane Ship has seen in the workspace, grouped
by repo:

- **kind badge** (`once` / `event` / `schedule`) mirrors the YAML
  trigger;
- **pattern** deep-links into `/catalog` so reviewers can read the
  pattern body in place;
- **last run** shows the reconciled status or "no runs yet" for
  freshly declared lanes;
- **Sync now** re-pulls `.ship/config.yml` — admin only.

Per-lane detail (`/lanes/<lane_row_id>`) shows the full raw config,
sync source (`<ref_sha>:.ship/config.yml`), and up to 20 recent runs
keyed to the lane.

## Migrating from the old "workflow artifact" world

RFC-0007 removed `artifact_kind=workflow` from the public surface.
What used to be a workflow artifact is now a starter lane:

| Before                                           | After                                                                 |
|--------------------------------------------------|-----------------------------------------------------------------------|
| `.github/workflows/ship-pr-and-ci-gate.yml`      | `lanes.pr_review.event: pull_request` + `pattern: pr-and-ci-gate`    |
| `.github/workflows/ship-scheduled-sdlc-lane.yml` | `lanes.daily.schedule: "0 9 * * *"` + `pattern: scheduled-sdlc-lane` |
| `.github/workflows/ship-onboard-seed-knowledge.yml` | `lanes.seed.once: install` + `idempotency_key: seed-v1`          |

If your repo still ships a hand-written workflow that hasn't been
migrated, the generator will refuse to overwrite it; delete the file
or rename it to get out of the way.

## Cookbook

### Add a new lane

1. Edit `.ship/config.yml`:

    ```yaml
    lanes:
      retro:
        schedule: "0 15 * * FRI"
        pattern: retro-assembly
    ```

2. `shipctl lanes install` to write
   `.github/workflows/ship-retro.yml`.
3. Commit `.ship/config.yml` **and** the generated wrapper in the
   same PR. The Console will pick it up on the next push to the
   default branch.

### Pause a lane temporarily

Comment out (or delete) the lane block and push. The backend cleans
up the `lanes` row on the next webhook tick; the generated wrapper
will stop being rendered by `shipctl lanes install` on the next run.

If you want a "pause" that keeps the wrapper file on disk, wrap the
wrapper's `on:` block with a GitHub Actions `if:` guard — but note
that most teams find "delete + re-add" simpler and more auditable.

### Trigger a lane manually from the UI

Not yet. `/lanes/<id>` reserves space for a "Trigger lane" button
and the backend already has the `PipelineRun.lane_id` column, but
the button itself is a future-phase item. For now the manual
override is the native GitHub Actions "Run workflow" menu, which
works on every `ship-<lane_id>.yml` wrapper.

### Keep the `lanes` table in sync

In normal operation you don't have to do anything — push-to-default
keeps the cache fresh. Use "Sync now" when:

- you rewrote history and the webhook didn't fire;
- you're debugging a parse error and need the backend's take on the
  current YAML;
- you just flipped a lane on/off and want the Console to reflect it
  without waiting for the next push.

## Troubleshooting

| Symptom                                                               | Cause                                                                          | Fix                                                                             |
|-----------------------------------------------------------------------|--------------------------------------------------------------------------------|---------------------------------------------------------------------------------|
| `/lanes` says "No lanes discovered yet" but the YAML has a `lanes:` block | Either (a) `.ship/config.yml` wasn't pushed to the default branch yet, or (b) webhook delivery hasn't landed. | Push the commit; if the webhook is lost, click **Sync now** on the repo card.    |
| "Missing `.ship/config.yml`" on sync                                   | Repo's default branch has no `.ship/config.yml`.                               | Run `shipctl init` or point the `default_branch` at the branch that has it.      |
| Lane row shows kind `event` but run never fires                       | The wrapper file wasn't regenerated after the YAML change.                     | Re-run `shipctl lanes install`, commit the updated wrapper.                      |
| Lane row stays `running` forever                                      | `workflow_run.completed` webhook delivery failed.                              | Re-send the delivery from the GitHub App settings → Advanced → Recent deliveries.|
| `lanes.sync` returned `synced_with_errors`                            | One or more lane entries failed schema checks.                                 | Inspect the audit log — the per-lane error messages are stored on the audit row. |
