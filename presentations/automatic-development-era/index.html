Work on Linear issue ELM-103

Registration. Error when selecting a plan

Team: Elmundi Bug ready:developer stage:developer Improvement ElMundi pre-release

Problem

  • On the Unlock ElMundi / registration flow, entering an email that already belongs to a user still triggers the OTP flow.
  • After email verification, on the plan selection screen, Start free trial fails with: "Failed to open checkout. Please try again."
  • The Login action is not prominent enough, so existing users may accidentally follow the registration path.

Objectives

  • Reduce failed checkouts and confusion for existing users by surfacing login and detecting existing accounts by email before or during sign-up, with clear messaging.
  • Restore a coherent path from plan selection to checkout (trial) for users who are allowed to proceed.

Expected behaviour

  1. Login visibility: The Login entry point on the Unlock / registration flow is visually more prominent than today (per product/design direction).
  2. Existing email: When the user attempts to register with an email already tied to an account, the product shows a clear, user-facing message (e.g. prompt to log in or use password recovery) instead of silently continuing into a broken flow.
  3. Checkout: Start free trial opens the checkout flow successfully for users who are permitted to start a trial, or the user sees a specific, actionable message if checkout cannot open (e.g. already subscribed, wrong session)—not only a generic failure.

Scope

  • Frontend: Unlock / registration UI, plan selection / trial CTA, Login prominence.
  • Backend / auth: Ability to detect existing user by email at the right step (registration or pre-OTP) without breaking security/privacy expectations.
  • Payments / checkout: Investigate why checkout fails (session, Stripe, eligibility) for the scenario above and align behaviour with product rules.

Non-goals

  • Redesigning the entire pricing or subscription model outside this flow.
  • Merging without explicit approval; do not move this issue to Done without human sign-off.

Risks

  • Email enumeration: Checking whether an email exists can be abused to infer account existence. Mitigation must align with security and product policy (e.g. rate limiting, same messaging patterns as login).
  • Payment / Stripe: Root cause of checkout failure may be backend or config; fix may span multiple services.

Classification

  • Primary: Bug (checkout failure after registration path for existing-account email).
  • Secondary: Improvement (login visibility, duplicate-email messaging).

Feature description

Fix the Unlock / registration journey so that existing-account emails are handled explicitly (login or recovery path) instead of progressing into OTP and a broken trial/checkout step. Increase Login visibility on the same flow. Ensure Start free trial either opens checkout for eligible users or surfaces specific, actionable errors (not a single generic message).

User stories

  1. As a returning user who mistook Unlock for sign-up, I want Login to be easy to find on the Unlock screen, so that I sign in instead of starting registration.
  2. As a user who enters an email that already has an account, I want a clear message before or early in sign-up (not only after OTP on pricing), so that I can log in or reset password without wasting steps.
  3. As a new user eligible for a trial, I want Start free trial to open checkout reliably after verification, so that I can subscribe without opaque failures.
  4. As a user who cannot start a trial (e.g. already subscribed or ineligible), I want a specific reason and next step, so that I know what to do instead of seeing a generic checkout error.

Acceptance criteria (BA)

  1. Login prominence: On the relevant Unlock / registration screen(s), Login is more visually prominent than in the current production behaviour, per agreed design (placement, weight, or hierarchy).
  2. Duplicate email: If the user submits an email that already belongs to an existing account on the registration path, the product shows an explicit, user-facing message and a path to log in and/or password recovery (per product/security policy). The user must not be left with the only outcome being failed trial after OTP with no earlier explanation.
  3. Checkout / trial: For users allowed to start a trial, Start free trial successfully initiates/opens the checkout flow (or equivalent) after plan selection. If checkout cannot open, the user sees a specific message (e.g. session, eligibility, already subscribed, configuration) and a clear next step, not only "Failed to open checkout. Please try again."
  4. Regression: New registration and trial for a genuinely new email still completes end-to-end.
  5. Privacy / abuse: Any server-side check that reveals whether an email is registered is implemented with mitigations agreed with security (rate limiting, consistent messaging, logging/monitoring as needed).

Edge cases

  • Email enumeration: Rapid or automated probing of "does this email exist?" — throttle, CAPTCHA or equivalent if required by policy, uniform response times where applicable.
  • Same email, different auth methods: e.g. password vs OAuth — messaging should guide to login without exposing unnecessary account internals.
  • Session mismatch: User verified OTP in one tab or stale session — checkout should fail gracefully with session refresh or re-login guidance where applicable.
  • Already subscribed / active trial: User reaches plan screen but is not eligible — specific copy and CTA (e.g. go to account, manage subscription), not generic checkout failure.
  • Stripe or config errors: Distinguish user-actionable (e.g. "try again", contact support) from internal errors (log/monitor; user sees safe generic fallback only if necessary).

Impacted components (initial)

  • Frontend: Unlock / registration screens, OTP step, plan selection / Start free trial CTA, error/toast copy, Login entry styling and placement.
  • Backend / auth: Registration and/or OTP initiation endpoints; optional email lookup or equivalent flow with security review; session/cookie handling for post-login checkout.
  • Payments: Stripe (or current provider) checkout/session creation for trial; eligibility rules and error mapping to user-visible reasons.
  • Analytics (if applicable): Funnel events for duplicate-email branch and checkout failures (for validation, not scope expansion).

Technical notes

  • Root cause split: (A) UX/auth — duplicate email allowed through to pricing; (B) checkout — failure may be eligibility, Stripe, or session. Implementation may require frontend + API + payments alignment; confirm actual stack in repo.
  • Enumeration: Prefer patterns aligned with existing login and password reset (same ambiguity vs explicit "email found" per product decision). Coordinate with security on copy and rate limits.
  • Errors: Map backend/Stripe codes to stable user-facing reasons; avoid leaking internal IDs in production UI.

Test plan

Manual (priority)

  1. New email: Full Unlock → OTP → plan → Start free trial → checkout opens (or expected redirect); complete or cancel safely.
  2. Existing email (core bug): Use a known registered email on Unlock registration → expect early explicit handling (no silent OTP-only dead end); no generic checkout failure as the first explanation of "already registered".
  3. Login path: From Unlock screen, Login is noticeable; user can reach login without hunting.
  4. Ineligible trial: Account already subscribed (or policy-defined ineligible) → Start free trial shows specific message, not only generic failure.
  5. Regression: Password recovery link still works from messaging if offered.

Automated (if present in repo)

  • E2E or integration for registration + checkout happy path; add cases for duplicate-email branch once API behaviour is fixed.

З чого починаємо

Ера автодеву: агенти всюди — а межа «webhook vs AI» не очевидна

  • Інструкції в чаті й UI вендора — немає diff, blame, rollback.
  • Модель «обирає» задачу за настроєм → неповторюваний конвеєр; інколи достатньо одного POST з CI замість ще одного «розумного» шару.
  • Зелений CI не пояснює, що саме зробив бот і чому.
  • Паралельні актори без меж → дублі PR, шум у трекері, росте вартість розбору.

Ship: спочатку машина станів і політика, потім LLM усередині ролі — webhook лишається тонким клеєм між системами.

«Просто AI» vs підхід Ship

Вісь Типовий AI-лайфстайл Ship
Інструкції Промпт у чаті / SaaS Markdown у репо, ревʼю як код
Наступна задача Контекст моделі Pick — скрипт, фільтри й сортування
Черга Невидиме «зробимо все» Колонки трекера + guards
Запуск Кнопка без розкладу Оркестратор (CI): слоти, одна job на роль
Аудит Важко відновити факти Run ↔ тікет ↔ маркер у коментарі
Гроші Модель на випадковому контексті Іменований throughput + вузький запуск агента

Визначення

Ship — не продукт, а набір правил і артефактів

  • Instruction-first: методологія й промпти в git (Apache-2.0), адаптація під ваш стек.
  • У репозиторії Ship: documentation/, prompts/, workflows/, tools/, приклади впровадження.
  • Ви переносите модель роботи до себе: трекер, CI, агент — змінні адаптери.

Скінченний автомат

Трекер — машина станів, не дошка «для краси»

Канон з reference: колонки й перехіди зафіксовані; бот не заходить у Backlog без людини.

Guards

Мітки й поля — API між людиною й машиною

  • «Готово до розробки» — не слова в Slack, а мітка/статус, який читає pick.
  • Після BA на картці ready:developer у Todo — інакше developer pick порожній (так і задумано).
  • Без guards бот робить не те, що думає команда.

Оркестратор

CI задає ритм: хто, коли, один тик — одна роль

  • У reference: GitHub Actions, окремий cron на intake / clarification / BA / developer.
  • Один run — одна job; зелений run ≠ «відпрацював developer» — дивимось заголовок і слот.
  • concurrency на етап — менше «рваних» pick при накладенні.
:10 intake → :25 clarification → :40 BA → :55 developer (парні UTC, приклад)

Picker / Pick

Вибір задачі — детермінований код, не LLM

З framework Ship: якщо модель обирає наступний тікет — зникає межа між політикою й імпровізацією.

  • Скрипти pick-*-issue.mjs: фільтр (проєкт, статус, мітки), сортування, максимум один тікет за запуск.
  • Pick можна юніт-тестити як звичайний код.
  • Порожній pick → job успішно завершується без агента (тиша — норма).

Launch

Запуск агента навмисно окремо від pick

  • Pick — яку картку взяли. Launch — як зібрати промпт, метадані, викликати HTTP API агента.
  • Зліпити в одне — кожен дебаг стає археологією: змінили wiring — «випадково» змінилась черга.
  • Тонкий клієнт з git (напр. cloud-agent-launch.mjs) читає версійовані промпти.

Промпти

Слова стають поведінкою — лише через git

  • Ролі: intake, clarification, BA, developer — окремі файли в prompts/cloud-agent/.
  • Виправлення «у чаті» не лікує headless: урок — PR у markdown, як для YAML.
  • База промпта: scope, preconditions, reporting (маркери), stops.

Інваріанти

Ідемпотентність: повторний тик ≠ другий світ

  • Перед роботою — перечитати тікет; якщо стан уже відображає прогон — вийти тихо.
  • Один відкритий PR на тікет SDLC, гілка fix/<ISSUE>-auto.
  • Маркер у коментарі ([GitHub SDLC:…]) звʼязує run і роль.

Дебаг

Порядок розслідування зафіксований у методології

  1. Pick / cron / guards — чи та картка взагалі потрапила в автомат?
  2. Launch — гілка, секрети, який промпт пішов у API?
  3. Текст промпта — лише після того, як черга чесна.

Пара «лог workflow run ↔ тікет у трекері» має відновлювати історію без шаманства.

Гроші й увага

Прозорий throughput дешевший за «нескінченну паралель»

  • Іменовані слоти (сітка) → чесна відповідь: скільки автоматизації ми спроєктували.
  • Хвилини агента не йдуть на випадковий вибір задачі — це робить дешевий pick.
  • Дублі й ретро «що хотів бот» — податок на ревʼюерів; Ship цілить у auditable velocity.

Підсумок

Automatic Development Era: тонкий webhook + чесна черга — дорога модель лише там, де треба зміст

Ship — черга в трекері, оркестратор, детермінований pick, агент у контурі. Повертаємось до теми: не множити «AI поверх усього», якщо подія вже визначена — спочатку контракт і прозорий тригер.
